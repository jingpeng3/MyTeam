# 流程路由 (Routing)

协调者在 **Intake 之后、Plan 之前**先跑本决策程序：把用户一句话目标映射到某个 plan 模板，或判定「这不是流程需求 / 没匹配模板」。判据在本文件，**候选与细节以各模板自身的 `routing` 块为单一事实源**（`coordinator/plans/*.json`），本文件不重复抄路由表，避免漂移。

## Step 0 — 是不是「流程需求」

先判断该目标是否值得起一个多 agent DAG（Job）：

- **是** —— 能拆成多步、需不同能力、要并行 / 评审 / 合成 → 进 Step 1 匹配模板。
- **否** —— 一次性问答、单步小改、纯查一条数据 → **不建 Job**，协调者直接处理或按需单点拉一个 agent。别为小事套流程。
- **是流程但下面无匹配模板** —— 走 `team-build`（对话式新建 DAG / 模板），别硬套一个不合适的模板。

## Step 1 — 匹配模板（先具体后通用，命中即停）

逐个读 `coordinator/plans/*.json` 的 `routing` 块，对每个候选看三项：

- `when` / `signals`：目标的意图或关键词命中它的适用场景吗？
- `not_when`：目标是否落在它的**排除边界**里？落了就跳过该模板。
- `required_slots`：命中后要收集哪些槽值。

命中某模板后即停，按标准实例化流程走：

```
plan <模板文件> --show-vars          # 看该模板需要哪些槽
# 按用户目标为各阶段现写 goal 值，写进 coordinator/plans/vars/<批次>.json
plan <模板文件> --as <批次id> --vars-file coordinator/plans/vars/<批次>.json
tick → wait 逐轮驱动
```

**评估顺序**：多个模板可能都沾边时，优先选**更具体 / 覆盖面更窄**的那个（如目标只要求其中一个子产物时，选只产出该子产物的窄模板，而非覆盖多个产物的宽模板）。`not_when` 正是用来把宽模板从窄目标里排除的。

## Step 2 — 歧义与兜底

- **多个模板都命中且难分具体度** → **暂停**，把候选列给用户让其选，**不要默认第一个**。
- **都不命中但确是流程需求** → `team-build` 新建模板 / DAG。
- **`required_slots` 缺信息** → 先问用户补齐，再实例化；**绝不把带 `{{槽}}` 的半成品 goal 发给 worker**（`plan` 也会拒）。

## 维护（单一事实源）

- 新增 / 修改模板时，**改的是该模板自己的 `routing` 块**（`when` / `signals` / `not_when` / `required_slots`）——这就是路由候选的唯一来源。
- 本文件只在**判据本身**变化时才动（如新增一类兜底规则），平时不随模板增删改动。
- `team-build` 新建 / 编排模板时应顺手写好 `routing` 块，从源头防漏。
